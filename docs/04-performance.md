# Performance plan

Nora has no measured performance yet. The numbers below are provisional project goals to calibrate against real hardware, not claims of superiority. Kitty documents separate throughput, latency and energy axes [S02]. Nora must report them separately too.

## Metrics and provisional targets

Use a named reference machine, a release build, a 120×40 viewport, fixed font/DPI, explicit history limit and opaque background. Also test large windows, splits and multiple refresh rates.

| Metric | Measurement | Initial goal |
| --- | --- | --- |
| Startup | Launch to first submitted frame; separately launch to visible test prompt | Warm median <100 ms; cold median <250 ms on reference desktop |
| Idle | CPU time/wakeups over 60 s after settling | <0.5% of one logical core; no periodic redraw if blink disabled |
| UI service | winit input callback to accepted PTY write | p95 <2 ms idle, <8 ms with a separate pane flooding |
| Echo pipeline | Input dispatch to frame submission containing uniquely tagged echoed text | p95 within one refresh interval +5 ms under declared load |
| Render preparation | Snapshot/font/geometry CPU times, warm glyph cache | p95 <2 ms for a 120×40 single pane; separately report GPU/surface waits |
| Engine processing | Headless feed to processed state with checksum | Track MiB/s and allocations; improve only measured bottlenecks |
| PTY processing | Emit fixed stream, append supported DSR marker, wait for reply | Compare same machine/settings; no universal MiB/s promise |
| Memory | RSS/PSS, CPU caches and estimated/queried GPU allocations | Initial empty-instance target <80 MiB RSS; explain font/driver contribution |
| Multi-pane fairness | Flood one pane, timed echo workload in another | No dropped bytes; report p50/p95/p99 and worst delay |

Do not count a missing display test as success. Startup definitions include whether font cache is warm and whether shader/device initialization is included. RSS excludes some GPU allocation; present both where available. Driver memory accounting is approximate and must be labeled.

## Three benchmark layers

### A. Engine and adapter, headless

Feed deterministic Rust-generated byte streams directly to the pinned engine. Benchmark parser/state updates and snapshot extraction separately. Include ASCII scrolling; ANSI colors/cursor movement; CJK/combining/fallback; alternate-screen TUI redraws; split UTF-8; and long-line wrapping. Verify final terminal state/hash before timing. Vary feed sizes (1 byte, 4 KiB, 64 KiB), geometry and history.

A parser-only test of `vte` is an optional diagnostic and must not replace engine-state timing. Rust `criterion` is a candidate tool, not a runtime dependency. Allocation counting is a development instrument; validate it does not distort production results.

### A.1 Headless engine benchmark tool (N26a)

Implemented in `src/dev/` (development instruments; no production code path depends on them) and validated by `tests/benchmark.rs`:

- **Corpus generator** (`src/dev/corpus.rs`, `Corpus`): deterministic, seed-driven byte streams — `ascii_lines(n)` (printable ASCII, 80 columns + `\r\n` per line), `unicode_lines(n)` (80 chars/line from a fixed Latin/Greek/Cyrillic/CJK/Devanagari/Ethiopic/symbol pool), `control_sequence_flood(n)` (cursor/SGR/clear/alt-screen sequences only), and `unique_glyphs(n)` (one unique code point per line, ascending from U+0100). Same seed + length ⇒ identical bytes; no external RNG dependency (inline SplitMix64).
- **Engine benchmark** (`src/dev/bench.rs`, `EngineBench` / `run_bench`): feeds a corpus to a fresh headless `Engine` in 4 KiB chunks and times **feed** (engine processing) and **snapshot** (state extraction) separately, plus total wall time, final-screen FNV-1a 64 state checksum, non-blank cell count, and build/machine metadata (package, version, profile, OS, arch, logical CPUs).
- **Interpretation**: feed time is engine processing only; snapshot time is state extraction, not presentation. Neither is a user-latency number. The state checksum pins correctness: a fast trial with a wrong final screen is a failure, not a fast sample.

Workload mapping: `ascii_lines` ≈ P01 (scrolling/parse), `control_sequence_flood` ≈ P02 (escape-heavy state work), `unicode_lines`/`unique_glyphs` ≈ P03/P05 (cell handling, warm-cache vs unique-glyph cost). P04 (alternate-screen TUI redraws) is covered by the alt-screen sequences inside the control flood; P06–P10 remain later N26 slices. The live-PTY (layer B) and renderer/input (layer C) instruments land in N26b.

### B. Live PTY, processing completion

Build a Rust child helper that puts its terminal into an appropriate raw mode, emits a fixed workload, appends a supported cursor-position request, and waits for its reply with a timeout. Do not time the generator's writes alone: kernel buffers may still contain unread bytes. Use a clean test session to distinguish the completion reply from unrelated input, and restore termios on normal/error paths.

DSR completion establishes that the stream was processed sufficiently to generate a reply; it does **not** establish screen presentation. For nora, supplement with internal sequence/byte counters for deterministic verification. Document the neutral DSR sequence and expectation using xterm semantics [S18]. External terminals have different synchronized-update behavior: verify support and never hide inconsistent rendering modes in one comparison table.

Use MiB/s = workload bytes / 2^20 / elapsed seconds. Pre-generate workloads or separately measure generation cost. Record output sizes, row count and final-state checksum so throughput is not gained by omitting work.

### B.1 Real PTY completion handshake (N26b)

Implemented in `src/dev/pty_bench.rs` and validated by `tests/pty_benchmark.rs`:

- **Handshake** (`PtyBench` / `run_pty_bench`): spawns the tagged-I/O helper child (`src/bin/nora_child.rs`) over a real PTY (`PtySession`, N05a) in `stop <n>` mode. The child reads its stdin until at least `n` bytes and a newline have been received, and only then prints the `STOPPED` completion marker — so the marker can appear only after the child has processed every byte nora sent. The benchmark pumps the session until the marker is visible in the engine grid (deadline-bounded at 10 s; a missed deadline is reported in `PtyBenchResult::completed`, not a hang).
- **Measured fields** (`PtyBenchResult`): `spawn_time` (session start), `feed_time` (enqueue + flush to the child), `completion_time` (time until the marker is visible), `total_time`, plus corpus bytes, viewport size, `completed`, the marker, and the N26a `BenchMetadata`.
- **Interpretation**: completion time is a real PTY round trip (child receipt + engine grid), not a timer on the writer's own accounting. It establishes processing completion, not screen presentation (layer B caveat above). Timings are informational on shared CI; the `completed` flag and corpus byte count are the correctness gates.

### C. Rendering and user experience

Measure full-frame CPU preparation and GPU timestamps if supported, atlas misses/evictions, upload bytes, draw calls, surface acquisition waits, input service and echo-to-submit. An instrumented test hook can associate a unique echoed marker with a snapshot revision and a submitted frame.

Software timestamps end at submission unless platform presentation feedback is captured. Even compositor feedback is not a physical key-to-photon measurement. Use a camera/photodiode setup when making physical latency claims; identify display refresh, compositor and input hardware. Do not infer low physical latency from fast parser throughput.

### C.1 Headless renderer and input instruments (N26b)

Implemented in `src/dev/render_bench.rs` and `src/dev/input_bench.rs`, validated by `tests/render_benchmark.rs` and `tests/input_benchmark.rs`:

- **Renderer** (`RenderBench` / `run_render_bench`): headless, no GPU. Feeds a full-screen deterministic corpus (N26a `Corpus`) to a fresh `Engine`, then times **prepare** (snapshot → draw items and background fills via the same pure mapping the GPU path uses, `crate::render::term`) and **submit** (flatten the prepared frame into a flat byte buffer — the CPU-side stand-in for the GPU vertex upload). `RenderBenchResult` records rows/cols, corpus bytes, draw-item and fill counts, `prepare_time`, `submit_time`, `total_time`, `submitted_bytes`, the N26a state checksum of the final screen, and `BenchMetadata`.
- **Input** (`InputBench` / `run_input_bench` / `InputEvent`): times the pure keyboard encoder (`crate::input::encode`) over a list of key events — no terminal state, no PTY, no display. `InputBenchResult` records event count, encoded count, sent-byte total, `encode_time`, `total_time`, and `BenchMetadata`.
- **Interpretation**: prepare/submit are CPU-side render-pipeline costs only — no surface acquisition, GPU timestamps or presentation are measured, and nothing here is a key-to-photon number. The state checksum (renderer) and the pinned N09a sent-byte total (input) are the correctness gates; timings are informational on shared CI.

## Workloads

| ID | Stream/interaction | What it detects |
| --- | --- | --- |
| P01 | 64 MiB newline-delimited ASCII | Scrolling/history/parse costs |
| P02 | 32 MiB mixed CSI styles and cursor changes | Escape-heavy state work |
| P03 | 16 MiB Unicode including combining/CJK/Ethiopic | Cell handling and font/cache churn |
| P04 | Repeated 120×40 alternate-screen redraws | Full-screen TUI rendering |
| P05 | Fixed glyph set, then many unique glyphs | Warm cache vs atlas thrashing |
| P06 | 1 MiB paste to deliberately slow child | Queue bounds, partial writes, cancellation |
| P07 | Flood pane A, tagged echo pane B | Responsiveness and fairness |
| P08 | 10,000-row history with search while output grows | Lock contention and stable search |
| P09 | Resize/font/DPI changes during output | Geometry races and cache invalidation |
| P10 | 60 s idle, focused/unfocused/minimized | Wakeups, blink and energy proxy |

Counts are suggested fixed corpus sizes; reduce for smoke tests without changing the recorded definition. Keep no sensitive terminal recordings in fixtures. Use synthetic data or attributed redistributable fixtures.

## Experimental procedure

1. Record commit, build/profile flags, OS/kernel, CPU/GPU/driver, compositor/backend, monitor Hz, font files/hash, size/scale, history and all nondefault settings.
2. Run two warmups then at least ten measured trials per workload; randomize terminal order. Report median and p95 with raw samples and dispersion. More repetitions may be needed for startup or physical latency.
3. Compare current kitty, Alacritty and Ghostty installations actually available. Record exact versions. Compare foot only on native Wayland after verifying its source/test contract. Run X11 and Wayland separately.
4. Align dimensions in cells and pixels/font metrics; report unavoidable differences. Test comparable presentation settings and a separate documented low-latency mode.
5. Verify correctness and completion for every trial. A timeout, dropped-byte result or corrupted final state is a failure, not a fast sample.
6. Store a small JSON result set and methodology in `docs/performance/`; large raw traces are local artifacts. CI smoke timing is informational; noisy shared CI does not enforce desktop percentile thresholds.

## Optimization order

Get correctness and measurements first. Then optimize the largest cost: avoid whole-history copies and repeated allocations; shorten locks; coalesce wakeups; cache font lookup/shaping/rasterization; retain row geometry; batch uploads/draws; balance read/write turns; finally evaluate LTO, renderer thread, alternate atlas implementation or allocator.

Require a before/after profile, a relevant workload and unchanged state/visual tests for each optimization. Regressions over about 10% deserve investigation, but a change within measurement noise is not evidence of a speedup. Do not loosen targets silently: record machine-specific baselines and the reason for any revised goal.

Avoid GPU parsing, one draw per cell, one task/thread per glyph, unconditional `ControlFlow::Poll`, arbitrary sleeps to hide flicker, or disabling rendering to advertise end-to-end speed. Wgpu present modes vary by backend; inspect capabilities rather than assuming mailbox/immediate [S16].
