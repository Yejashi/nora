# Performance baseline (2026-10-15, M3)

Method: `scripts/perf.sh` on the release build, run in the live GNOME
Wayland session on the host GPU (AMD Radeon RX 6750 XT, RADV), x86_64
NixOS, 1211 font faces installed (422 files, 300 MB). Startup is the
median of five `nora -- true` runs. Throughput streams a 32 MiB text
corpus with SGR colors through `cat` and subtracts the child's 1 s delay
and the startup median. Frame costs come from `NORA_TRACE_FRAMES`. These
are single-machine numbers, not cross-hardware claims. Input latency is in
[2026-10-15-input-latency.md](2026-10-15-input-latency.md).

## Startup

Traced with `NORA_TRACE_STARTUP=1` (milliseconds since process start):

| Stage | Before | After |
| --- | --- | --- |
| Display connection | 2.5 | 2.4 |
| Window created | 69 | 70 |
| Fonts loaded | 1078-1093 | 122-126 |
| GPU device and surface ready | 1125-1139 | 169-185 |
| First frame presented | 1130-1144 | 176-193 |
| System fallback fonts installed (background) | (part of the above) | 695-721 |

Cause: every launch scanned all installed fonts twice. Once in nora's
own style lookup, and once inside cosmic-text's `FontSystem::new_with_fonts`,
which calls `load_system_fonts` despite taking an explicit font list.
Fixes: fonts resolve through fontconfig's cache (`fc-match`, `fc-list`),
the startup font system holds only the resolved faces, and the full
system-wide font system (for per-glyph fallback) is built on a background
thread and swapped in when ready.

`nora -- true` wall time: 1161 ms before, 204-214 ms after.

## Throughput and frames

| Metric | 80x30 (15 pt) | 160x60 (6 pt) |
| --- | --- | --- |
| Throughput, 32 MiB `cat` | 56.2 MiB/s | 56.7 MiB/s |
| Frames during the stream | 5 | 5 |
| Frame total, median / p95 | 2.67 / 4.90 ms | 2.95 / 7.91 ms |
| Scene build, median / p95 | 0.06 / 0.17 ms | 0.28 / 0.50 ms |
| GPU encode, median / p95 | 0.88 / 4.36 ms | 1.76 / 7.02 ms |
| Present, median / p95 | 0.32 / 2.59 ms | 0.42 / 2.67 ms |
| Peak RSS during the stream | 73 MiB | 76 MiB |

Throughput repeated three times at 80x30: 56.5, 56.1, 56.6 MiB/s. The
headless path (no window, no snapshots) parses the same corpus at about
110 MiB/s, which bounds what the window path can reach.

Changes measured in this round:

- **Snapshot backpressure.** The pump built a full-grid snapshot under the
  terminal lock on every wake, even while the window still held an undrawn
  one, stalling the PTY reader. It now snapshots only when the pane's slot
  is empty, and the window wakes it after each frame. In the first runs
  (script arithmetic corrected afterwards) the stream time went from
  about 1680 ms to about 490 ms.
- **Filter fast paths.** The prompt-marker and graphics filters walked
  every byte. They now copy or skip plain runs to the next ESC. Profile
  share before: 12.5% and 4.4% of the reader thread; the headless parse of
  the corpus went from 0.33 s to 0.30 s.

## Profile (reader thread, before the filter change)

`perf record` of the windowed stream: `Term::input` 30%, prompt-marker
filter 12.5%, `Row::reset` 5.7%, graphics filter 4.4%, vte ground state
4.0%. The renderer was not a bottleneck (5 frames over the stream).
